Core principles

pure-cbor makes two promises that usually pull against each other: functional code you can read, and the fastest standard CBOR in JavaScript. These six principles are how the code keeps both. Each one is shown with the code that carries it out.

On this page

1. Explicit state over hidden state

A decoder needs a cursor, a nesting depth and some limits. Rather than keeping them in a class instance or module variables, pure-cbor puts them in one plain record. The record is created for a single decode call and passed down by argument, so every function that touches it says so in its signature.

Encoding works the same way. The output is a Writer record holding bytes and a cursor. Functions that write take the writer and return nothing, or take a position and return the next one. Nothing else changes.

The README lists every resource shared between calls: constants and a tag lookup, the standard UTF-8 encoders and decoders, two scratch areas used only within one synchronous call (a one-element float array and the owned-output staging buffer), and one cache that does outlive a call. Variants, not classes

CBOR tags and simple values become immutable values made by tagged() and simple(). They are recognised by a private, frozen prototype rather than by their shape, so a plain object that happens to have tag and value fields is still just an object. The only class in the library is CborError, used on the cold error path.

2. Options choose functions; loops never check them

Encode options (floats: 'shortest' and deterministic: true) are not stored on the writer and tested per value. They are turned into a frozen EncodeProfile once, and the profile selects which write function runs. The default write function has no option checks in it at all.

3. Allocation is a policy the caller picks

The README says to choose the API by the lifetime of your data, not merely its speed. There are three encode policies, and no codec module depends on which one is in use.

PolicyAPIWhat you get
Owned output (default)encode(value)Exactly sized, with no shared backing buffer. The bytes can be kept or transferred to another worker.
Caller-owned bufferwrite(binary, offset, value), encodeInto(value, bytes, offset)Writes into your memory and returns the next offset. A capacity error never partially writes the destination.
Slab-backed (opt-in)createSlabEncoder(options)Appends values into one shared slab. Earlier views are never overwritten; values above maxPooledValueSize get exact owned output instead.

6. Performance is measured, one process per benchmark

Each workload in the benchmark runs in its own Node process. The README explains why: workloads sharing a process skew each other's V8 type feedback by up to 2×. Results are the median of 5 × 80 ms rounds, and BENCHMARK.md treats anything within about ±10% of 1.0 as level, because repeated runs of the same code moved that much.

Measurements decide the shape of the code, and the code records them where they apply. Here a helper that would read more cleanly was kept out of the object loop, because V8 did not reliably inline it:

The design records go further: DESIGN-coverage.md lists two "cleaner" refactors that measured slower and were reverted. Correctness is checked before speed, too. Before timing, every workload must round-trip exactly through pure-cbor and read back identically in cbor-x and cborg. The performance notes collect each of these choices with its measured effect.
