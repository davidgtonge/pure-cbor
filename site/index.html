pure-cbor · CBOR for JavaScript and TypeScript

From a value to bytes and back, through every line that matters

pure-cbor implements CBOR (RFC 8949) in about 2,800 lines of strict TypeScript, with no runtime dependencies. This page is one walk through it. Try the codec first; it is the real library, running in your browser. Then follow a value through the code: the principles it is built on, the encode path, the decode path, streaming, and how we know it is fast and correct.

  • npm: pure-cbor
  • Plain ESM with TypeScript declarations
  • No Node APIs, no generated code (CSP-safe)
  • MIT licence

Try it Start the tour npm

Two promises

1

Clean, functional code

Pure functions over explicit state, in the spirit of OCaml. There are no classes apart from the error type, and no state kept between calls apart from two documented caches: decoded map keys, and one write function per encode-option set (which holds no data). Tagged values and simple values are immutable variants, and the wire format is described by one named set of constants.

2

The fastest standard CBOR library for JavaScript

Pure JavaScript, with no native addon. On public benchmark data it decodes 1.16–1.71× faster than cbor-x, the next fastest library measured, and encodes level with it up to 1.50× faster. Small messages decoded from a fresh buffer are 5–12× faster.

It covers the whole RFC 8949 data model (tags, bignums, dates, Map, simple values, typed arrays), deterministic encoding, CBOR sequences over Web Streams, and COSE, CWT, WebAuthn and mdoc messages, which are checked against their published test vectors. It is standard CBOR only: there is no private wire format.

Try it

Type a JavaScript value, or pick an example, and see the exact bytes pure-cbor writes, what each byte means, and the value decode gives back. Switch to Decode hex to read any CBOR, including malformed input. This runs the library built from src/ on main.

A JavaScript literal: objects, arrays, strings, numbers, 12n, true/false/null/undefined, new Map([[k, v]]), new Date('…'), new Uint8Array([…]) and the other typed arrays, tagged(tag, value) and simple(n). It is parsed, never evaluated.

Encode options

Spaces, line breaks and a 0x prefix are ignored. Decoding uses the defaults: duplicate keys, invalid UTF-8 and trailing bytes are errors.

    Part 1

    Core principles

    pure-cbor makes two promises that usually pull against each other: functional code you can read, and the fastest standard CBOR in JavaScript. These six principles are how the code keeps both. Each one is shown with the code that carries it out.

    1. Explicit state over hidden state

    A decoder needs a cursor, a nesting depth and some limits. Rather than keeping them in a class instance or module variables, pure-cbor puts them in one plain record. The record is created for a single decode call and passed down by argument, so every function that touches it says so in its signature.

    Encoding works the same way. The output is a Writer record holding bytes and a cursor. Functions that write take the writer and return nothing, or take a position and return the next one. Nothing else changes.

    The README lists every resource shared between calls: constants and a tag lookup, the standard UTF-8 encoders and decoders, two scratch areas used only within one synchronous call (a one-element float array and the owned-output staging buffer), and one cache that does outlive a call. That cache is documented where it lives:

    Variants, not classes

    CBOR tags and simple values become immutable values made by tagged() and simple(). They are recognised by a private, frozen prototype rather than by their shape, so a plain object that happens to have tag and value fields is still just an object. The only class in the library is CborError, used on the cold error path.

    2. Options choose functions; loops never check them

    Encode options (floats: 'shortest' and deterministic: true) are not stored on the writer and tested per value. They are turned into a frozen EncodeProfile once, and the profile selects which write function runs. The default write function has no option checks in it at all.

    The same idea runs down to single functions. The number writer has a separate writeShortest, rather than a flag on write, so that the default stays small enough to inline into the array and object loops:

    3. Allocation is a policy the caller picks

    The README says to choose the API by the lifetime of your data, not merely its speed. There are three encode policies, and no codec module depends on which one is in use.

    6. Performance is measured, one process per benchmark

    Each workload in the benchmark runs in its own Node process. The README explains why: workloads sharing a process skew each other's V8 type feedback by up to 2×. Results are the median of 5 × 80 ms rounds, and BENCHMARK.md treats anything within about ±10% of 1.0 as level, because repeated runs of the same code moved that much.

Before timing, every workload must round-trip exactly through pure-cbor and read back identically in cbor-x and cborg. The performance notes collect each of these choices with its measured effect.

    Part 2

    Encode, step by step

    Owned encoding writes a value once into a reusable staging buffer, then copies the used bytes out once. There is no sizing pass, and the output is one exactly sized allocation. As you scroll, the panel follows { id: 7, name: 'Ada' } through each step: the function that is running, and the bytes it is responsible for.

    1. encode(): the front door

    The public encode lives in allocation.ts, because it is an allocation policy. Options leave on the first line. Numbers, booleans, null, undefined and typed arrays have sizes known up front, so they are written straight into an exactly sized array with no writer at all. Strings go directly into staging memory. Everything else is staged.

    2. staged(): one growable pass

    The staging buffer is the only module-level memory the encoder uses, and it holds no data between calls: take must copy what it needs before staged returns. If an exotic input such as an accessor property calls encode again in the middle, the inner call gets a private buffer instead. A buffer that grew past 64 KiB is not kept.

    The README gives the reason for this design: in V8 every typed array over 64 bytes is a separate off-heap allocation of about 0.5 µs, so allocation count dominates. Writing once into reused memory and copying out once gives one output allocation and no sizing pass.

    3. writerFor() picks the write function

    For the default profile this is a single identity comparison. Other profiles get a separate recursive writer, built once and kept in a Map. Principle 2 shows how profiles are chosen.

    4. writeValue(): the dispatcher

    The dispatcher tests the common types first: scalars, then arrays, plain objects, byte strings and typed arrays. The rarer variants are moved into a second function, writeRareValue, which keeps the hot one small. Containers get nestedDepth(depth), which fails with depth-limit at 128 levels. That limit also turns cyclic input into a typed error.

    5. Scalars and the argument header

    writeScalar returns the new position, or NOT_SCALAR so the dispatcher can carry on. It asks the writer for room first: 9 bytes covers any number.

    Safe integers are always CBOR integers in their preferred width, so millisecond timestamps reach other languages as integers. Everything else, including -0 and NaN, is binary64 by default:

    Every header goes through writeArgument, which picks the smallest width for the argument. It writes byte by byte, with no DataView:

    6. The Writer cursor

    A growable writer reallocates on demand; a fixed writer wraps caller memory and never grows, because its capacity was checked before writing began. Loops that keep the cursor in a local variable call roomFor, which stores the position back only if it has to grow.

    7. Arrays: a local cursor and inline scalars

    The array writer keeps position in a local variable and spells out the scalar cases rather than calling writeScalar. Only nested items go back through the dispatcher, which is passed in as a parameter so that array.ts does not import codec.ts.

    8. Plain objects and the back-patched header

    Only objects whose prototype is Object.prototype or null are encoded as maps; dates, class instances and boxed primitives are rejected rather than flattened. Keys are enumerated with for…in, and the own-property check runs only if Object.prototype has gained enumerable properties.

    The entry count is only known after the loop, because properties set to undefined are skipped. So the writer reserves one header byte, which is enough for up to 23 entries, and fills it in at the end. A larger map shifts its entries right by the extra header bytes, which keeps the preferred, smallest header.

    9. Map: any keys, inline COSE shapes

    A Map knows its size up front, so its header is written first. Keys and values share one helper with inline paths for the shapes COSE uses: integer and short text keys, and byte-string and scalar values.

    10. Strings: reserve, write, patch

    Text uses the same trick as objects. The header is reserved for the string's UTF-16 length, the UTF-8 bytes are written, and the header is corrected afterwards, moving the payload only if the width changed. When the destination is tight, the exact size is computed first so a capacity error never leaves a partial write.

    11. Deterministic encoding

    With deterministic: true, optionsWriter collects each map's entries and writes them in the order of their encoded keys (RFC 8949 §4.2.1). Two keys that encode to the same bytes, such as 1 and 1n in one Map, are a duplicate-key error.

    12. Caller memory: measure first, never write partially

    encodeInto and write use a fixed writer over the caller's bytes. Scalars check their own size. For anything else, a cheap upper bound is measured first; only if that bound exceeds the free space is the exact size measured, and a capacity error thrown before any byte is written.

    The README notes the trade-off: for arrays and objects this guarantee costs a sizing pass, so owned encode() can be faster for objects.

    Part 3

    Decode, step by step

    Decoding a scalar touches no state at all. Decoding a container creates one small state record for that call and passes it down explicitly. The panel now reads the same 14 bytes back.

    1. decode() and binary()

    decode wraps the bytes in a Binary descriptor and reads exactly one item. The descriptor has no cursor and, deliberately, no DataView.

    The comment explains why: building a DataView means reading .buffer, which forces V8 to move a small fresh array's bytes off-heap. The README measures that at about 900 ns per message, more than the encode or decode itself.

    2. readItem(): scalars need no state

    The top-level reader switches on the major type in the first byte. Integers, simple values, floats, text and byte strings are read straight from (bytes, offset). Only arrays, maps and tags create a DecodeState, once, for their whole tree. A whole-value read returns the value itself; read returns a [value, nextOffset] pair so callers can walk a sequence.

    3. createState() and the limits

    The state record is built once, with its limits already validated. Its item budget starts at the number of bytes left. Every container subtracts its declared item count on entry; since each item needs at least one byte, a valid message can never exceed its own length.

    The defaults are 1,000,000 elements per array, 1,000,000 entries per map and 128 levels of nesting. Tags count toward depth too, so deep input fails with depth-limit instead of overflowing the stack.

    4. readValue(): the nested-item dispatcher

    Every nested item goes through here. A token below 24 is a small unsigned integer and is its own value, so it returns before the switch. Definite text is decoded inline with no result tuple, and definite byte strings in the default 'copy' mode go through Arena.copyByteString.

    5. The array loop

    The declared length is checked against maxArrayLength and against the bytes remaining before anything is allocated. Then the result array is preallocated. The first part of the loop, shown under principle 5, handles small integers, float64 and true/false/null/undefined. The rest handles text and wider integers inline, and hands anything nested to readValue.

    6. The map loop

    In the default 'auto' mode, a map whose keys are all text becomes a plain object. The object loop lives inside MapCodec.read itself rather than a helper, and small unsigned integer values are decoded inline. A __proto__ key becomes an own data property through Object.defineProperty: no prototype pollution, and no renaming.

    If a non-text key appears, the entries read so far move into a Map and decoding carries on there, keeping their order. Duplicate keys are found by counting once per map rather than checking each key. A Map tells keys such as byte strings and arrays apart by identity, so those are compared as CBOR values: byte strings by their bytes, the rest by their deterministic encoding.

    7. The decoded-key cache

    Repeated keys are the norm in CBOR data: a hundred rows share six key names. readTextKey skips the cache for one-character ASCII keys, which V8 already interns, and otherwise asks the cache before decoding.

    The cache is a 1,024-slot table for keys of up to 32 bytes. A hit is confirmed byte for byte, so a hash collision only costs a miss, and only keys that decoded as valid UTF-8 are stored.

    8. Text

    Short text, up to 32 bytes, is decoded in JavaScript: ASCII eight bytes at a time, then a strict UTF-8 decoder. Anything those don't accept goes to the native TextDecoder, so strict and replacement behaviour are exactly the native ones. readPayload is kept small so V8 can inline it into the array and map loops.

    9. The byte-string arena

    COSE and WebAuthn messages are mostly byte strings: keys, signatures and certificates. In the default 'copy' mode each must be independent of the input, but a separate copy over 64 bytes costs an off-heap allocation each. So byte strings over 64 bytes from one decode are copied into one shared arena.

    BENCHMARK.md records the effect: since 0.6.0 a COSE or WebAuthn message costs about one allocation, which halved the default mode's time on those flows. The trade-off is documented too: one result can keep its siblings' bytes alive. binaryOwnership: 'copy-separate' gives every byte string its own buffer, and 'borrow' returns views into the input.

    10. Tags

    RFC 8746 typed-array tags read their byte-string content directly into the right typed array. Every other tag decodes its content (counting toward maxDepth), then converts it: a caller's decoder first, then the built-ins for dates, bignums and the self-described marker, otherwise an immutable Tagged value.

    11. Limits for hostile input

    The README lists what the decoder guarantees against hostile input:

    • Every container's declared length is checked against its limit and the remaining input before anything is allocated.
    • The per-decode item budget, bounded by the input length, stops a chain of nested headers from preallocating far more than the message could contain.
    • Deep input fails with depth-limit instead of overflowing the stack. Encoding enforces the same depth limit, which turns cyclic input into a typed error.
    • Duplicate map keys are rejected by default, and invalid UTF-8 is rejected by default.

    It is also clear about what this is not: a full memory-budget guarantee. Apply message byte limits at the transport boundary too. The limits are validated once, by a function shared with the streaming scanner so both report the same errors:

    Part 4

    Streaming

    A CBOR sequence (RFC 8742) is complete CBOR items written back to back. Over a network they arrive in chunks, and an item can be cut anywhere. pure-cbor decodes the items that sit inside a chunk in place, and gathers the rest with a scanner that reads headers only.

    Two layers

    sequence.ts is an incremental core with no stream APIs in it. It can be fed from WebSocket messages, Node 'data' events or tests. stream.ts is a thin layer of Web Streams and async-iterator adapters over it, which touches stream globals only when called.

    Items across chunk boundaries

    Most items sit wholly inside a chunk and are decoded in place, exactly like a normal decode. Only the end of a chunk needs care.

    Three constants govern this, each commented with its reason:

    The boundary scanner

    scanItem walks headers only and skips payloads by their declared length. It decodes nothing, allocates nothing and does not recurse: one counter, itemsPending, tracks how many items the current item still needs (an array adds its length, a map twice its entry count, a tag one). Indefinite-length items push the counter onto a small stack until their break.

    The scan can stop at any byte and resume later from its saved state, so an item spread over many chunks is scanned once in total. That is what keeps decoding linear in the input whatever the chunking.

    Two details keep errors identical however the input is chunked. The scanner checks array and map limits in the same order as the decoder, using the same containerLimits. And for any malformed header it calls deferToDecoder, which ends the item just after the bad header so the decoder reads it and reports its own error.

    Decoding in place, scanning near the end

    Within a chunk the decoder calls the ordinary read. Only in the last SCAN_AHEAD_BYTES does it scan first. If a truncated error still escapes the decode, the scan settles whether the item really was cut off.

    BENCHMARK.md explains the scan-ahead: exceptions had cost about 3.7 µs per chunk boundary, almost all of it stack-trace capture. With 1 KiB chunks, 100,000 rows took 55 ms before the change and 35 ms after.

    The assembly buffer

    An item that runs past the end of a chunk is copied into an assembly buffer, a new one for each spanning item, so values that borrow from it stay valid. Each later chunk feeds it in blocks of at least ASSEMBLY_BLOCK bytes until the scan reports the item complete. Then it is decoded once, and normal decoding resumes in the chunk just after the item's end.

    The decoder's public surface is two methods. A decoder that has thrown stays failed, push after end() or from inside its own callback is a TypeError, and errors carry absolute stream offsets.

    Bounded buffering

    maxItemBytes (default 16 MiB) caps one item's encoded size. For an item still arriving, the scanner checks it from headers, before the bytes arrive, so a short header claiming a 4 GB string can't make the decoder buffer it. The other decode limits (maxDepth, maxArrayLength, maxMapEntries and the allocation budget) apply to each item.

    The Web Streams adapters

    decodeStream is a TransformStream around one decoder. With batch: true it emits one array per input chunk instead of one value per step: each Web Streams step costs about 1 µs in Node, more than decoding a small value.

    decodeSequence is an async generator over a ReadableStream or any iterable of chunks. Stopping early cancels the source.

    Encoding sequences

    The encoder has two modes. With chunkBytes: 0 (the default) each value becomes its own owned chunk, for the lowest latency. With chunkBytes: N values are written straight into a growable chunk, which is emitted once it holds at least N bytes. An unsupported value throws and leaves no partial bytes behind.

    Part 5

    Performance notes

    The README says each performance choice was measured, and the reasons are commented in the code. This part collects them: what the trick is, why it exists, and the effect the docs record. All numbers are Node 22 on macOS arm64; browser and workerd performance are not yet measured.

    Headline numbers

    The benchmark suite runs each workload in its own Node process, because workloads sharing a process skewed each other's V8 type feedback by up to 2×. The chart shows the five public corpus workloads. Hover over or focus a bar for the underlying times.

    Where it is not ahead

    BENCHMARK.md says to treat anything within about ±10% of 1.0 as level. Outside the corpus:

    • Arrays of short strings, decoded: 0.92–0.97× cbor-x. The time goes on allocating many tiny strings, which every library pays.
    • Long text from a reused buffer (ASCII 4096): about 0.9×. pure-cbor's TextDecoder is strict and rejects invalid UTF-8; cbor-x's replaces it. With fresh input they are level.
    • Encoding 64-byte strings: cborg is 8% faster (0.92×). Mixed arrays and the nested config object are level within noise.
    • COSE and WebAuthn: pure-cbor copies byte strings by default, while cbor-x returns views into the input. It matches cbor-x only with binaryOwnership: 'borrow'.
    • cbor-x records mode, a non-standard wire format, decodes 100 rows about 2.6× faster than pure-cbor by generating readers with new Function. pure-cbor stays standard CBOR and avoids code generation.

    The full tables, including fresh-input decoding, are at the end of this part; the streaming numbers are in Streaming.

    On-heap and off-heap typed arrays

    Most of the design follows from one property of V8 that the docs describe: a small, freshly allocated typed array lives on the JavaScript heap and is cheap, but a typed array over 64 bytes, or a small one whose .buffer is touched, needs a separate off-heap backing store. BENCHMARK.md puts that at about 0.5 µs. For small messages that costs more than the encoding or decoding itself.

    So the library avoids touching .buffer on small arrays, and counts allocations:

    • Owned encoding writes into a reused staging buffer and copies out exactly once: one output allocation and no sizing pass (encode, step 2).
    • Small owned outputs (numbers, simple values) are allocated at their exact size and never touch .buffer, so they stay on-heap.
    • The slab encoder exists for larger messages: outputs of 64 bytes or less are already cheap on-heap allocations, so a slab mainly saves the off-heap allocation above that size.
    • Byte strings over 64 bytes from one decode share an arena (decode, step 9).

    No DataView for scalars

    A DataView is the usual way to read big-endian numbers, but constructing one on a fresh small buffer forces that buffer off-heap. The README measured the cost at about 900 ns per message, more than the encode or decode itself. pure-cbor reads and writes headers and integers byte by byte, and converts floats through a one-element scratch array:

    Shaping code for the inliner

    Several functions are spelled out where a shared helper would read better, because V8 declined to inline the helper into a hot loop:

    • Array and map loops keep the cursor in a local variable and write scalars inline. A shared helper measured 10–20% slower (README).
    • The object decode loop stays inside MapCodec.read. Moving it one call deeper made small-object decoding bimodal (principles, 6).
    • Number writing has separate write and writeShortest functions, so the default stays small (principles, 2).
    • Text decoding keeps readPayload small and moves the native decoder into decodeNative.

    Wire constants are const enums for the same reason. The comment in header.ts records the alternative it replaced:

    Objects: enumeration, duplicates, keys

    Allocation-free enumeration

    Object keys are read with for…in, which goes through V8's enum cache with no allocations: about 3× faster than Object.keys plus Object.values (README). An own-property check is added only if Object.prototype has gained enumerable properties, so a polluted prototype never leaks keys.

    Counting instead of checking

    Duplicate keys are detected by comparing the object's key count with the entry count once per map, about 4× cheaper than checking each key (README). The cost is precision: the duplicate-key error points at the map header, not the repeated key.

    The decoded-key cache

    A new key string has to be internalized by V8 each time it becomes a property name. A 1,024-slot cache returns the same string for repeated keys of up to 32 bytes (decode, step 7). Its comment records the effect:

    Together with the single-pass, back-patched map writer and small integers decoded inline, these are what BENCHMARK.md credits for the object results: one row decodes in 210 ns against cbor-x's 301 ns, and 100 rows in 21.1 µs against 29.1 µs (reused input).

    Arrays and short text

    Array decode preallocates the result, measured 1.6× faster than push; holey arrays had no measurable cost for consumers. Scalars are decoded inline with no per-element tuples.

    Short ASCII text (up to 32 bytes) is checked 8 bytes at a time, and the tail is built by a single exact-arity fromCharCode call. Short non-ASCII text uses a strict JavaScript UTF-8 decoder that defers to TextDecoder on anything malformed. On reused input, ASCII 32 decodes in 53 ns against cbor-x's 119 ns.

    Long text is where this stops helping. At 4096 bytes both libraries hand the work to TextDecoder, and pure-cbor's strict decoder is about 0.9× cbor-x's replacing one on a reused buffer.

    Byte strings and typed arrays

    Typed arrays are copied with one bulk Uint8Array.set; overlapping source and destination views are supported. A 1 MiB Float64Array encodes in 51.9 µs against cbor-x's 119.6 µs, and decodes in 51.1 µs against 116.6 µs.

    Byte strings are where the default copy policy costs the most. COSE and WebAuthn messages are mostly byte strings, and each copy over 64 bytes is a separate allocation. Version 0.6.0 added the per-decode arena and inline Map and byte-string encode paths. BENCHMARK.md measured the change in one process against 0.5.0:

    Borrow mode (binaryOwnership: 'borrow') returns views into the input, as cbor-x does by default. It is the fastest, and safe while the input stays unchanged, which is the normal case when verifying a message.

    Streams

    • Scan ahead near chunk ends. An exception at every chunk boundary cost about 3.7 µs, mostly stack-trace capture. Checking the boundary with the scanner first took 1 KiB chunks from 55 ms to 35 ms per 100,000 rows (streaming).
    • Batch mode. Each Web Streams step costs about 1 µs in Node. Moving values as one array per chunk makes batched decodeStream within 8% of the core decoder.
    • Lazy sources. Enqueuing many items into a ReadableStream up front made Node's stream queue quadratic: 100,000 items took 2.7 s to read back. The README advises building sources that pull lazily, and encodeSequence does.

    Where cbor-x is level or ahead, and why

    • Arrays of 3–7 character strings, decoded (0.92–0.97×). The time is dominated by allocating many tiny strings, which every library pays.
    • Long text decoded from a reused buffer (ASCII 4096, about 0.9×). pure-cbor's TextDecoder is strict; cbor-x's silently replaces invalid UTF-8. With fresh input they are level.
    • Mixed and tiny-object encoding (mixed[], nested config): level within noise.
    • Encoding 64-byte strings: cborg is 8% faster (0.92×). At that size every library pays one off-heap allocation for the output.
    • cbor-x records mode is not in the tables: it is a non-standard wire format both ends must speak. Measured separately, it decodes 100 rows in about 8.6 µs, 2.6× faster than pure-cbor, and halves the bytes, by generating object readers with new Function.

    Wire size

    pure-cbor writes preferred (smallest) map headers; cbor-x's standard encoder always writes a 3-byte map header unless variableMapSize: true. One object row is 57 bytes against 59; 100 rows are 5,868 against 6,068. cborg writes smaller floats, so it produces the smallest output for float-heavy data.

    Reproduce

    Part 6

    How we know it's correct

    Speed is only worth having on top of correct output. The test suite checks pure-cbor against the RFC's own examples, against the published vectors of the formats that use CBOR for security, and against other libraries, and it feeds it hostile input on purpose.

    One error type, one contract

    Every validation failure is a CborError with a code and a byte offset. The hostile-input tests rely on this contract: malformed input may only produce a value or a CborError, never a RangeError from a blown stack or an out-of-bounds read.

    tryDecode turns that into a discriminated result. It catches library validation errors only, not arbitrary programmer or runtime errors:

    RFC 8949 Appendix A

    Every example in RFC 8949 Appendix A decodes. Every example JavaScript can represent exactly also encodes back to the same bytes. (Integral floats such as 1.0 are JavaScript integers, so they encode as integers.) Further golden vectors cover integer and float widths, text and UTF-8 header boundaries, and non-preferred argument widths, which are accepted when decoding.

    Real-world vectors

    The vectors in test/vectors are public, openly licensed examples from the specifications and projects where CBOR carries security-sensitive data:

    FormatSourceWhat is checked
    COSEThe COSE working group's examples (RFC 8152/9052)All 63 example messages decode and re-encode byte for byte, and 31 rebuilt Sig_structure/MAC_structures match the signed bytes exactly.
    CWTRFC 8392The claims decode as expected from the signed and MACed tokens.
    WebAuthnW3C Web Authentication Level 3 test vectorsAll 15 attestations parse, with the correct COSE keys (ES256/384/512, RS256, Ed25519, Ed448). Truncated and padded authenticator data are detected.

    "Kept as written" uses a custom tag decoder, a feature that exists for exactly this: re-encoding signed data byte for byte.

    Differential and round-trip tests

    • Interoperability. 2,000 random trees are checked both ways against cbor-x. The public corpus is checked both ways against cbor-x and cborg, including cborg's half-precision floats and sorted keys. Dates, bigints, Map and undefined are checked against cbor-x in both directions, and the stream encoder and decoder against cbor-x's EncoderStream and DecoderStream.
    • Deterministic encoding. The RFC 8949 §4.2.1 key order is reproduced regardless of insertion order, and deterministic output equals cborg's canonical output byte for byte on the public corpus.
    • Round trips. 2,000 seeded random nested trees go through owned, prepared and slab encoding; 20,000 seeded scalar round trips; the public and generated corpus. Random trees with every value kind (bigint, Date, Map with byte-string keys, Tagged, simple values) round-trip in all three encode modes, and encodedSize agrees with the output.
    • Text. 20,000 short-text cases are checked against TextDecoder in strict and replace modes, since the JavaScript fast path must agree with the native decoder exactly.
    • Inline fast paths for Map and byte strings are checked against the general paths, and float arrays decode identically through the byte path and the DataView path.

    The comparison libraries are optional. Install them to run the differential tests:

    Streaming under every chunking

    • Every split point of a mixed sequence, every chunk size from 1 to 64 bytes, and 200 random chunkings decode to the same values.
    • A linear-time check: 4× the data takes about 4× the time, so quadratic rescanning would fail.
    • Malformed input gives the same error code under every chunking.
    • Limits, absolute offsets, cancellation, lazy pulling and both batch modes; borrowed values stay valid as later chunks arrive.

    Hostile input

    • 30,000 random and container-heavy malformed inputs, which may only produce values or CborErrors.
    • Depth bombs and nested allocation bombs: limits are checked before allocating.
    • Every truncation point fails without reading outside the supplied view.
    • Prototype pollution in both directions: a __proto__ key decodes as an own data property, and a polluted Object.prototype never leaks keys into encoded objects.
    • Capacity errors never partially write the destination, for nested values too, and an exotic input that re-enters encode() still gets correct output.
